# TRAINING_DATA_GUIDE — Synthetic Data Generation for Hive/Swarm Cells

> Canonical status: active
> Created: 2026-07-27
> Read this before: generating training data for any Cell's distillation pipeline

## 0. The Principle

Every Cell's training data is **synthetic** — generated by frontier teacher models (Claude Opus 4.8, GPT-5.5 Pro/Thinking, Gemini 3.1 Pro) using each Cell's system prompt as the instruction template. No human-labeled data is required, except for:

1. **Seed intents** (100 per Cell) — hand-written by the Hive team to cover the Cell's input space
2. **Eval sets** (300-5K per Cell) — hand-curated to measure punch-up
3. **Adversarial sets** (200 per Cell) — crafted to test safety/robustness

## 1. Data Generation Pipeline

### 1.1 Architecture

```
┌─────────────┐    ┌──────────────┐    ┌─────────────┐    ┌──────────────┐
│ Seed Intents│───>│ Input        │───>│ Cell System │───>│ Teacher      │
│ (100/human) │    │ Augmenter    │    │ Prompt      │    │ Model        │
└─────────────┘    └──────────────┘    └─────────────┘    └──────┬───────┘
                          │                                     │
                          ▼                                     ▼
                   ┌──────────────┐                    ┌──────────────┐
                   │ Mutation     │                    │ Filter &     │
                   │ Engine       │                    │ Schema Check │
                   └──────────────┘                    └──────┬───────┘
                                                              │
                                                              ▼
                                                   ┌──────────────────┐
                                                   │ (instruction,    │
                                                   │  completion)     │
                                                   │  → JSONL         │
                                                   └──────────────────┘
```

### 1.2 Components

**Seed Intents** — 100 hand-written examples covering:
- Normal usage (70%)
- Edge cases (15%)
- Adversarial/out-of-scope (15%)

Each seed intent is a structured record:
```json
{
  "id": "intent_007",
  "cell": "intent_classifier",
  "category": "normal",
  "input": "Go to the pricing page and tell me what the enterprise plan costs",
  "expected_output_schema": "{route: string, confidence: float, reason: string}",
  "expected_route": "browser_navigate",
  "difficulty": "medium",
  "tags": ["navigation", "pricing", "multi-step"]
}
```

**Input Augmenter** — For each seed intent, generate 50 variants by:
1. Paraphrasing (using GPT-5.5 Instant as paraphraser)
2. Adding/removing context noise
3. Changing specificity level (vague → specific)
4. Switching domain (same intent, different topic)
5. Translating register (formal → casual, technical → layman)

**Mutation Engine** — Create harder variants:
- Add typos and grammatical errors
- Introduce ambiguous references
- Insert irrelevant context
- Combine multiple intents
- Add temporal constraints ("later", "after this")

**Teacher Prompt** — Format as:
```
<|system|>
{Cell system prompt}
<|user|>
{augmented input}
<|assistant|>
```
With structured output constrained via JSON schema enforcement (for GPT-5.5 Pro) or XML template enforcement (for Claude Opus).

**Filter & Schema Check** — Discard any teacher output that:
- Violates the Cell's output schema
- Exceeds Cell's max context length
- Contains disallowed content (PII, unsafe responses)
- Fails inter-teacher agreement (≥2/3 teachers must agree on structure)

## 2. Per-Cell Data Strategy

### 2.1 Router Family (intent, spam, urgency, link_scorer, retrieval_ranker)

**Generation approach**: Classification-style data. Each seed intent produces N variants with known ground-truth labels.

**Input format**:
```json
{
  "message": "user utterance or page content",
  "context": {"active_tab": "...", "recent_actions": ["..."]}
}
```

**Output format**:
```json
{
  "route": "browser_navigate",
  "confidence": 0.97,
  "reason": "User explicitly asked to navigate to pricing page"
}
```

**Special considerations**:
- Adversarial inputs must include prompt injection attempts, ambiguous requests, and out-of-vocabulary intent classes
- Confidence calibration is critical — generate data where the correct answer is low-confidence (ambiguous intents)
- For spam detector: include legitimate messages that resemble spam (false positive hard examples)

**Seed diversity**:
| Dimension | Values |
|-----------|--------|
| Routes | browser_navigate, browser_search, browser_capture, browser_hibernate, swarm_ask, swarm_research, swarm_code, swarm_organize, system_preference, system_help, out_of_scope |
| Confidence | 0.5-1.0 (normal), 0.0-0.5 (edge, include calibrations) |
| Noise level | clean, 1 typo, 2 typos, grammar errors, ambiguous pronouns |
| Context richness | no_context, single_tab, multi_tab, space_context |

### 2.2 Browser Family (DOM scout, action planner, nav reasoner)

**Generation approach**: Trace-based generation using Playwright browser automation + teacher reflection.

**Data generation steps**:
1. Use Playwright to navigate to 5,000 diverse web pages (top 5K from Chrome UX Report)
2. For each page, record: page URL, DOM tree (simplified), rendered text, viewport state
3. Generate 5 action goals per page (e.g., "find the login button", "extract the main article text")
4. Have teacher model generate the optimal action plan + expected DOM state after action
5. For nav reasoner: simulate multi-step navigation sequences across 1,000 multi-page flows

**Input format**:
```json
{
  "dom": "<simplified DOM tree>",
  "viewport": {"width": 1200, "height": 800, "scrollY": 0},
  "page_url": "https://example.com/pricing",
  "goal": "Find the enterprise pricing and click 'Contact Sales'"
}
```

**Output format** (action planner):
```json
{
  "steps": [
    {"action": "scroll_to", "target": "#enterprise-section", "reason": "Enterprise info is below the fold"},
    {"action": "click", "target": "a.contact-sales", "reason": "Primary CTA for enterprise"},
    {"action": "wait_for", "condition": "form.contact-form visible", "timeout_ms": 5000}
  ],
  "fallback": "If contact form doesn't appear, look for 'Book a demo' link"
}
```

**DOM scout output**:
```json
{
  "elements": [
    {"selector": "#pricing-table", "type": "table", "role": "pricing_table", "confidence": 0.95},
    {"selector": "nav.main-nav", "type": "navigation", "role": "primary_nav", "confidence": 0.99}
  ],
  "interactive": ["button.cta-primary", "a.contact-sales", "input#email"],
  "content_summary": "3 pricing tiers: Starter $29/mo, Pro $99/mo, Enterprise custom"
}
```

**Special considerations**:
- DOM pages must be diverse: static, SPA, infinite-scroll, paginated, modal-heavy
- Include pages with accessibility issues, missing alt text, poor semantics
- Include pages with ads, cookie banners, interstitial popups (noise)
- Test with pages in 10+ languages

### 2.3 Coder Family (1B, 8B, sheet, document, presentation specialist)

**Generation approach**: Task-based generation from real code repositories + synthetic tasks.

**Code data sources**:
- 10K open-source Swift repositories (GitHub, MIT/Apache licensed)
- 5K Python repositories (data science, web, CLI tools)
- 5K TypeScript repositories (React, Node.js, API servers)
- Hive's own codebase (Sources/HiveCore, Sources/HiveBrowser)

**Task generation**:
1. For each repository, extract a "snapshot" — 5-15 files that form a coherent unit
2. Generate 5 coding tasks per snapshot (bug fix, feature add, refactor, test, document)
3. Have teacher model produce: solution diff, test file, explanation
4. For 8B coder: tasks span multiple files, require cross-file understanding

**Sheet specialist data**:
- 2,000 CSV/TSV datasets from Kaggle, data.gov, Socrata
- Generate 10 transformations per dataset (filter, sort, group, pivot, formula, chart)
- Output: correct formula or transformation result
- Special focus: dates, currencies, edge cases (empty cells, mixed types)

**Document specialist data**:
- 1,000 markdown documents with complex formatting (tables, code blocks, footnotes)
- Generate formatting tasks: apply style guide, restructure, add cross-references
- Output: properly formatted document

**Presentation specialist data**:
- 500 presentation outlines (from Make-a-Deck skill patterns)
- Generate slide-by-slide content + visual layout specs
- Output: structured slide deck with content + design tokens

**Input format** (1B/8B coder):
```json
{
  "task": "Add error handling to the API client for network timeouts",
  "files": {
    "Sources/ApiClient.swift": "existing file content...",
    "Sources/Models.swift": "existing file content..."
  },
  "repo_context": {"language": "swift", "style_guide": "hive", "test_framework": "swift-testing"}
}
```

**Output format**:
```json
{
  "plan": "1. Create a NetworkError enum 2. Modify URLSession wrapper 3. Add retry logic 4. Update callers",
  "changes": {
    "Sources/ApiClient.swift": "diff content...",
    "Sources/Models.swift": "diff content..."
  },
  "tests": {
    "Tests/ApiClientTests.swift": "test file content..."
  },
  "explanation": "Using async/await with retry mechanism..."
}
```

### 2.4 Planner Family (1B, 8B)

**Generation approach**: Session-trace-based planning from browser usage logs.

**Data generation**:
1. Record 5,000 complete browser sessions (synthetic, generated by Playwright navigating on instruction)
2. For each session: initial state, sequence of user actions, final state
3. Generate planning tasks from session halves (first half → predict second half)
4. Teacher generates optimal plan for completing the session goal

**Input format**:
```json
{
  "goal": "Research best project management tools and create a comparison",
  "session_state": {
    "tabs": [
      {"url": "...", "title": "...", "captured": true, "honeycomb_ids": ["src_001", "src_002"]}
    ],
    "project": {"id": "proj_001", "name": "Tool Research"},
    "memory": {"recent_claims": ["Asana has good timeline view", "Monday.com is expensive"]}
  }
}
```

**Output format**:
```json
{
  "plan": [
    {"step": 1, "action": "browser_navigate", "target": "https://www.g2.com/categories/project-management", "expected_info": "G2 category comparison"},
    {"step": 2, "action": "tab_capture", "scope": "main_table", "expected_info": "captured comparison data"},
    {"step": 3, "action": "swarm_ask", "query": "Compare top 5 tools by user count, pricing, key features", "source_scopes": ["captured_data"]}
  ],
  "estimated_steps": 6,
  "estimated_tokens": 15000,
  "key_milestones": ["Feature matrix created", "Pricing comparison", "Final recommendation"]
}
```

### 2.5 Librarian Family (100M, 1B)

**Generation approach**: Retrieval-augmented data from Honeycomb-style knowledge bases.

**Data generation**:
1. Create 10,000 synthetic "Honeycomb" entries (sources, claims, captures, artifacts)
2. Generate 10 retrieval queries per entry (direct, ambiguous, multi-hop)
3. Teacher model ranks relevant entries + extracts supporting evidence
4. Train librarian to reproduce teacher's ranking + extraction

**Input format**:
```json
{
  "query": "What did we decide about the authentication approach?",
  "sources": [
    {"id": "src_045", "title": "Auth Architecture Decision", "text": "We chose OAuth2 with PKCE...", "recency": "2026-07-20"},
    {"id": "src_032", "title": "Security Review Notes", "text": "OAuth2 flow reviewed by security team...", "recency": "2026-07-18"}
  ]
}
```

### 2.6 Auditor Family (1B, 8B)

**Generation approach**: Deliberate-error injection into correct outputs.

**Data generation**:
1. Take correct outputs from other Cells (coder, planner, research)
2. Inject 1-3 realistic errors per output (wrong API call, missing edge case, logical inconsistency)
3. Teacher model audits (correct output, error-injected output) → identifies errors
4. For 8B auditor: inject errors into multi-step plans with subtle dependencies between steps

**Input format**:
```json
{
  "original_task": "Implement a function to calculate Fibonacci numbers",
  "output_to_audit": "func fib(_ n: Int) -> Int { if n <= 1 { return n } else { return fib(n-1) + fib(n-2) } }",
  "output_errors": []
}
```

**Output format (detected)**:
```json
{
  "errors": [
    {"type": "performance", "severity": "high", "location": "line 3", "description": "Exponential time complexity, no memoization", "fix": "Add memoization cache"}
  ],
  "quality_score": 0.6,
  "pass": false
}
```

### 2.7 Summarizer Family (compressor, title_generator, memory_compressor)

**Generation approach**: Long-text → short-text paired generation.

**Title generator data**:
- 10K web pages (article text extracted) + human-written titles (from OpenGraph metadata)
- Generate synthetic: page text → multiple title candidates
- Teacher scores candidates for relevance, clarity, click-worthiness

**Memory compressor data**:
- 5K synthetic daily activity logs (based on Rewisp patterns: app switches, pages viewed, tasks done)
- Target: one-paragraph daily summary preserving action items and decisions

### 2.8 Reasoner (8B)

**Generation approach**: Chain-of-thought with verification.

**Data generation**:
1. Take 3K complex reasoning problems (from MATH, GSM8K, ARC, Hive-specific planning tasks)
2. Generate: problem → detailed step-by-step reasoning → final answer
3. Use GPT-5.5 Thinking + Claude Opus 4.8 as teachers
4. Train 8B reasoner to reproduce the chain-of-thought, not just the answer

**Special structure**: Step-by-step reasoning must be explicit, with each step's dependencies tracked:
```json
{
  "steps": [
    {"step_id": 1, "content": "The user wants to research project management tools...", "depends_on": [], "type": "understanding"},
    {"step_id": 2, "content": "First, I'll search for G2 comparison pages...", "depends_on": [1], "type": "search_plan"},
    {"step_id": 3, "content": "Then extract pricing and feature data from top results...", "depends_on": [2], "type": "extraction_plan"}
  ],
  "conclusion": {"answer": "..."}
}
```

### 2.9 Research Synthesizer (8B)

**Generation approach**: Multi-source document synthesis.

**Data generation**:
1. Collect 5K document sets (3-10 sources each) covering diverse topics
2. Generate: sources → synthesized brief with inline citations
3. Teacher ensures: every claim has source evidence, conflicting sources noted, uncertainty labeled
4. Train model on source-attribution and citation placement

### 2.10 Conversation (8B)

> **Conversation Cell created in Pass 27** at `conversation/8b_conversation.md`. Distilled from Notion AI, Claude Voice Mode, Gemini 3 Pro webapp, ChatGPT Agent Mode, Claude Cowork, GPT-5 personalities.

**Generation approach**: Multi-turn dialogue from session traces.

**Data generation**:
1. Extract 10K conversation turns from synthetic Hive sessions
2. For each turn, include: conversation history, Honeycomb memory state, current tab context
3. Teacher generates: natural response with optional tool calls
4. Train on: context-aware conversation that uses memory without announcing it

### 2.11 Tutor / Voice (100M)

**Tutor data** (from Gemini Guided Learning + Gizmo patterns):
- 500 lesson plans across 10 subjects
- Generate: student state → Socratic dialogue turn
- Teacher evaluates: learning gain, engagement, correctness

**Voice data** (from Claude Voice Mode + ElevenLabs + Sesame Maya):
- 2K dialogue turns with natural speech patterns
- Features: turn-taking, filler words, confirmations, interruptions
- Output: natural language with conversation markers

## 3. Quality Filters

### 3.1 Automatic Filters (applied to every generated example)

| Filter | Threshold | Action |
|--------|-----------|--------|
| Schema compliance | 100% | Reject if output fails schema validation |
| Max context length | Cell-specific | Truncate input or reject |
| Toxicity score | <0.01 | Reject (using Detoxify or equivalent) |
| PII detection | Zero tolerance | Reject if any PII detected |
| Inter-teacher agreement | ≥2/3 | Reject if <2 teachers produce structurally similar output |
| Output length ratio | 0.1-10x input | Flag outliers for manual review |
| N-gram overlap (dedup) | <80% | Deduplicate near-identical examples |
| Language detection | Target language >95% | Reject code-switched or wrong-language examples |

### 3.2 Manual Review (sampling)

| Phase | Sample Rate | Reviewers |
|-------|-------------|-----------|
| Seed intent generation | 100% | Hive team |
| Phase 1 data | 5% | Automated + 2 team members |
| Phase 2 data | 1% | Automated spot-check |
| Phase 3 data | 0.5% | Automated spot-check |
| Eval sets | 100% | Hive team |

## 4. Storage & Versioning

### 4.1 Data Format

All training data stored as JSONL with schema:
```json
{
  "id": "uuid-v7",
  "cell": "intent_classifier",
  "phase": "1",
  "teacher": "gpt-5.5-instant",
  "seed_intent_id": "intent_007",
  "input": {"...": "..."},
  "output": {"...": "..."},
  "metadata": {
    "generated_at": "2026-07-27T12:00:00Z",
    "teacher_model_version": "gpt-5.5-instant-2026-07-15",
    "token_count_input": 342,
    "token_count_output": 89,
    "schema_valid": true,
    "quality_score": 0.97
  }
}
```

### 4.2 Versioning

| Artifact | Version Scheme | Storage |
|----------|---------------|---------|
| Seed intents | git (hive-data/seed/{cell}/v{int}) | GitHub LFS |
| Generated data (Phase 1-2) | git (hive-data/generated/{cell}/{phase}/v{int}) | GitHub LFS |
| Eval sets | git (hive-data/eval/{cell}/v{int}) | GitHub LFS (read-only) |
| Trace data (Phase 3) | S3/cloud bucket + git SHA pointer | Cloud storage |
| Model checkpoints | Sweep/Mlflow experiment ID | Cloud storage |
| Evaluation reports | git (hive-data/reports/{cell}) | GitHub LFS |

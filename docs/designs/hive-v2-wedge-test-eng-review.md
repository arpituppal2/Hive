Findings:

**[P0] (confidence: 10/10) git state of main — the plan's premise 4 is false as committed.**
The plan states "The reset cleared tracked product code." It did not. Commit
850613b9 ("Reset main") deleted zero files (`git diff --diff-filter=D` between
850613b9^ and 850613b9 returns empty); main still tracks all 1,255 v1 files
including `Sources/Hive/WebChromeHandler.swift` and every test. The fresh-start
state exists only as 1,164 *unstaged* working-tree deletions. Consequences for
an agent team: any agent running `git status` sees a half-deleted tree; any
`git add -A` either resurrects all of v1 into main or permanently stages mass
deletion depending on intent nobody recorded; the salvage baseline
(archive/v1 tag) and live tree are confusable. Fix before W1 day one: commit
the working-tree deletions so main truly is the scaffold, then point agents at
`git show archive/v1:<path>` as the ONLY salvage channel. This is the single
cheapest, highest-leverage change in this review.

**[P1] (confidence: 9/10) plan lines 139-147 — bridge inventory is a name list, not a protocol.**
Missing for agent execution without ambiguity:
- Message envelope: request id, correlation of `ask.stream-chunk` to its
  request, terminal-state semantics (`done` vs `refused` vs error).
- Error message type: inventory has `capture-failed` but no error shape for
  `nav.go` failures, `omnibox.submit` failures, store errors. Every handler
  needs one error contract or agents will invent five.
- `ask.cancel`: v1 had `agent.cancel`; a streaming local generation with no
  cancel message means users eat the full generation or agents improvise.
- Delimiter convention: `capture-failed` is hyphenated while everything else
  is dot-delimited. Trivial now, annoying forever in a typed inventory.
- Security: v1's bridge required a per-session token injected into served HTML
  precisely because arbitrary web pages could reach the scheme handler. The v2
  plan's security posture covers prompt injection but never mentions bridge
  origin control. Carry the token pattern forward; it is written down in
  `WebChromeHandler.swift`'s header for a reason.
Deliverable: a one-page BRIDGE-SPEC.md with the envelope, full per-message
payload schemas, error enum, cancel semantics, and token handshake.

**[P1] (confidence: 8/10) memory residency has no budget table (extends prior reviews' flag).**
Prior reviews said "test model+CEF residency at W2 not W4." Agreed, and make
it concrete so W2 can actually fail or pass:

| Component | M1 8GB resident estimate |
|---|---|
| macOS base | ~2.5-3.5 GB |
| CEF (browser + GPU + N renderers) | ~1.5-2.5 GB |
| 4B @ 4-bit weights (unified mem) | ~2.3-2.6 GB |
| KV cache + Metal buffers | ~0.3-1 GB (context-dependent) |

That sum pages under memory pressure with a browser open. Required plan text:
a memory budget table, lazy model load on first ask, idle unload timer,
`DispatchSource.makeMemoryPressureSource` handling that drops the model first,
and a documented fallback ladder (Qwen3-4B → 2B-class) with the measurement
that selects between them at W2. llama.cpp mmap may win here precisely because
MLX loads eagerly; that belongs in the W1 rubric as a scored criterion, tied
to the floor machine.

**[P2] (confidence: 8/10) plan line 115-118 — span/chunking spec is underspecified.**
"Clamped to 20-120 words" leaves undefined: how paragraphs >120 words split
(sentence boundary? hard cut?), whether <20-word chunks merge with neighbors,
and what `charStart/charEnd` index INTO (must be the stored normalized
extraction string, not live DOM, or offsets rot on recapture). Agents will
each invent a different chunker. Required: pseudocode for the splitter +
span ID scheme (`{captureID}:v{n}:{spanIdx}`) + unit tests on fixture
documents. Deterministic algorithm, one owner file.

**[P2] (confidence: 8/10) plan lines 123-125 — refusal threshold undefined.**
"if no span clears relevance" is not implementable until "clears relevance"
has an operational definition: top-k retrieved, minimum BM25 score tau,
calibrated on the founder's dev captures, plus behavior when k < 1. BM25
scores are corpus-dependent and drift as the corpus grows; the threshold needs
a recalibration story or the ≥95% correct-refusal gate is unfalsifiable.

**[P2] (confidence: 7/10) verifier circularity in the golden-set gate.**
The gate scores "answers whose cited spans actually support them," but the
support checker is a second pass of the same-class small model. Verifier
errors directly contaminate the metric. Mitigation: hand-label a ≥20-question
calibration subset, report verifier precision/recall against it, and pin
decode parameters (temperature 0 or fixed seed) for gate runs so the gate is
reproducible.

**[P2] (confidence: 6/10) CDP E2E feasibility unproven until proven.**
Nine scripted flows over CDP in CI (W4) is the right target but the harness
isn't demonstrated on this CEF build. Spike ONE flow (launch → navigate →
assert) over `connectOverCDP` by end of W2. If attach fails on the vendored
CefSwift pin, you want that knowledge in W2, not W4.

**[P3] (confidence: 6/10) `session.restore` semantics undefined.** Payload,
persistence location for tabs (SQLite?), and the race between chrome load and
restore replay are unspecified. This is one of the nine gated flows, so it
needs a definition, even a small one.

**[P3] (confidence: 5/10) weights integrity.** Resumable download UX is
specified; SHA256 pinning + storing the weights license text in-repo is not.
Add both; redistribution obligations depend on it.

No other architecture issues found. Single-window, single-chrome-layer,
read-cite-only is the right blast-radius posture; there is genuinely little to
hijack and the plan says so explicitly.

Test-strategy assessment: the three-tier structure (contract test merge gate,
nine-flow CDP E2E, golden-set eval) is the right shape and matches the skill's
decision matrix (flows spanning 3+ components → E2E; LLM quality → EVAL).
Gaps the plan should absorb:

1. Contract test resurrection must adapt the v1 regexes to v2 file layout and
   the NEW message names; the old patterns key on `api('hive.x')` in `app.js`
   and `register("hive.x")` in `WebChromeHandler*.swift`. Keep those
   conventions deliberately or port the patterns consciously.
2. Injection fixtures need a defined home: extractor level (hidden text
   stripped?) AND model level (delimited untrusted block refuses to steer).
   Both layers, both tested.
3. Golden-set composition is unspecified: counts per bucket (how many of the
   50 are out-of-corpus?), who authors expected answers, expected-answer
   format. At n=50 with ≥95% refusal accuracy, a 10-question out-of-corpus
   bucket allows ZERO misses. State exact bucket sizes or enlarge them.
4. Telemetry privacy is testable and should be: a unit test asserting the
   opt-out build path issues no network writes.

## 4. Performance review

- Latency budgets absent (prior reviews flagged; concur, add numbers):
  propose p50/p95 on M1 8GB — capture ≤500ms click-to-saved; first ask token
  ≤2.5s (model warm), ≤8s cold (includes load); full grounded answer ≤12s
  warm; verify pass adds ≤150ms/claim. Put these in the W2 exit criteria so
  slippage is visible weekly, not at the W4 gate.
- The validate-retry loop multiplies generation cost on the unhappy path
  (draft + up to one regeneration + N verify passes). Bounded by design, good,
  but the ≤12s warm budget above must be validated WITH retries occurring.
- FTS5 over paragraph spans at wedge scale (thousands of captures) is
  trivially fast; no concern. Watch only the refusal-threshold drift noted
  above.
- Model unload/idle policy is a performance AND correctness item (A3);
  single owner file, one timer, one pressure handler.

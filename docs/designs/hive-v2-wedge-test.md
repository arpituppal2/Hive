## Problem Statement

v1 shipped the right thesis with broken execution: a macOS CEF browser whose UI was
"fundamentally impossible to use" (founder's words), built as a three-layer chrome
(SwiftUI + `hive://` web chrome + native webviews) where every feature needed three
coordinated edits. Waitlist users churned. On 2026-08-23 the entire repo was archived
(tag `archive/v1`, branch `archive/v1-20260823`, plus a source tarball) and `main`
was reset to a scaffold carrying reference material only.

The restart question is not "how do we rebuild v1" but "what is the smallest real
product that answers whether anyone besides the founder wants this."

## Demand Evidence

- Founder pain, daily, personal — and nothing else yet. No observed external user.
- Waitlist exists (now private) but churned on quality; churn is evidence of interest,
  not of demand for v2.
- Founder stated the objective function explicitly: "My life goal is roughly 8 million
  liquid. If this won't help me get there, I'd rather trash the project."
- Category context (Aug 2026): OpenAI is retiring Atlas this month; Comet survived a
  year of public exploits and litigation; Dia (Atlassian) is the last dedicated AI
  browser standing — Apple-Silicon-only, cloud-processed memory, $20/mo Pro publicly
  panned. Consumers don't pay for browsers; professional/enterprise knowledge workers do.
- Consequence: demand must be *measured*, not assumed. The build includes written kill
  criteria (see Success Criteria) and the instrumentation needed to score them (see
  Measurement).

## Status Quo

Founder's own duct-tape stack: browser + ChatGPT/Claude tabs + notes app + re-explaining
context every session. Nobody else has been observed solving this problem — that gap is
the top risk and the first assignment.

## Target User & Narrowest Wedge

User zero: the founder — ex-Perplexity, research-heavy days, allergic to losing context.
The wedge sentence: **"Your browser remembers what you read and answers with citations,
locally."** v2's job is to find five non-founder humans for whom that sentence is daily
reality. The enterprise/professional pivot (where the money signal in this category
lives) is a hypothesis this test may surface, not a commitment. Cohort makeup:
~25 of the 50 testers are recruited from research-heavy professions (legal,
finance, health, academic/analyst work) — the segment this category actually
monetizes and whose signal the current gate would otherwise miss entirely.

## Premises

1. Demand is founder-only until 5 watched users say otherwise; YC claims wait for that.
2. Read-and-cite-first, NOT act-first — no swarm, no Code Studio, no autonomous agent,
   no privileged actions in v2. Security consensus (Trail of Bits, UW, OWASP) says
   act-first architectures are structurally exploitable; read-cite is the safer class.
   Captured page content is still untrusted input (see Security posture) — read-cite
   reduces, not eliminates, injection risk.
3. One chrome layer, executed to the Zen bar using Zen/Brave shipped patterns — the
   bar is a scored checklist (see Chrome quality spec), not an adjective.
4. Restart ≠ amnesia: mine `archive/v1` for working parts (CEF integration patterns,
   adblock FFI wrapper, honeycomb FTS schema) instead of re-solving solved problems.
   Correction (eng review): the reset did NOT clear tracked product code — main still
   tracks all 1,255 v1 files as *unstaged* working-tree deletions. Before W1: commit
   the deletions so main truly is the scaffold; treat `git show archive/v1:<path>` as
   the only salvage channel; and maintain a SALVAGE-MANIFEST.md listing the exact
   files (with archive commit hashes) allowed into v2 — nothing off-list gets
   imported, or the 333-file v1 app target contaminates the wedge. Caveat: v1's reader
   mode was CSS-injection only; there is no extraction implementation to salvage.
   (Ignored build artifacts and empty dirs remain on disk until manually cleaned.)
5. The wedge is demoable in one take on an M-series Mac.

### Chrome quality spec

Quality gates catch broken; they do not produce excellent — v1 died on exactly that
confusion. The chrome gets an achievement mechanism, not just a bar:

- **CHROME-SPEC.md (W1, written before any chrome or bridge code)** — the single doc
  agents implement against: window-region diagram (left sidebar with integrated
  traffic lights, one toolbar — omnibox/nav/capture/ask — content, ask panel);
  design tokens seeded from Zen's measured values (34px collapsed rail, 48px compact
  min-width + 6px gutter, transitions 120–200ms ease-out, nothing bounces); motion
  table; per-component state tables (loading/empty/error/success/partial — every
  empty state gets warmth plus a primary action, never blank); keyboard map
  (Cmd+T/W/L, Cmd+Shift+A, arrow-key tab navigation, visible focus rings, 4.5:1
  chrome-text contrast, ≥28px hit targets); window-breakpoint rules (auto-collapse to
  the rail below ~900px width).
- **Design-system disposition:** v1's MASTER.md is reference-only; no teal/orange/
  Inter tokens carry forward into chrome source. Type pairing Manrope + JetBrains
  Mono (proven in the Comet reference); dark-first default.
- **Zen bar = scored checklist**, evaluated twice (end of W2, end of W4) on the floor
  machine; <7/8 means chrome is not done and blocks external exposure regardless of
  E2E green. Eight criteria: (1) sidebar slide ≤200ms, named easing, 60fps, no jank;
  (2) 34px rail toggle persists across restart; (3) traffic lights integrated, no
  double titlebar; (4) tab anatomy — favicon, truncated title, ≥24px close target,
  unmistakable active state; (5) omnibox focus ring, inline progress, Cmd+L; (6)
  blind side-by-side vs Zen at three matched states — indistinguishable or favorable;
  (7) keyboard completeness with focus visible everywhere; (8) motion restraint — no
  bounce/overshoot, reduced-motion honored.
- **Screenshot-diff CI (lands W3):** ~15 canonical chrome states (first run, 0/1/40
  tabs, capture in-flight, ask open, error pages, collapsed rail) diffed alongside
  the nine-flow suite — flows prove it works; screenshots prove it looks intended.
- **Taste ritual:** daily founder dogfood — reached for Safari, file a chrome bug;
  weekly Friday screenshot review, ten states beside Zen equivalents, losers get
  tickets; W4 reserves explicit polish capacity driven by scoring #2.
- **Decided before W2 starts:** sidebar ships pinned + collapse-to-rail (compact-
  overlay deferred post-test); ask surface is docked panel OR overlay sheet — pick
  one in W1; tab overflow at 40+ tabs defined; first-run download/empty-state
  sequence written; citation click-through specified (tap highlights the stored span
  / opens a reader view — the proof-of-memory moment gets designed, not described).

### Performance & memory budgets

Residency on 8GB is arithmetic, not hope: macOS base ~2.5–3.5GB + CEF ~1.5–2.5GB +
4-bit 4B weights ~2.3–2.6GB + KV cache ~0.3–1GB sums past headroom with a browser
open. Policy: lazy model load on first ask; idle unload timer; a memory-pressure
handler that drops the model first and evicts background-tab renderers before load;
under pressure the ask degrades instead of hanging — context clamped to ~top-8 spans
(≤600 words), tokens streamed, failure surfaces as a plain "try again." Fallback
ladder Qwen3-4B → 2B-class selected by measurement at W2; mmap-vs-eager-load scores
in the W1 rubric.

Latency budgets on the floor machine, measured from W2 so slippage shows weekly
instead of at the W4 gate: capture click→saved ≤2s (p50 target ≤500ms); first
streamed ask token ≤3s warm / ≤15s cold including model load; complete grounded
answer ≤12s warm even when validate-retry fires (verify ≈≤150ms/claim).

### Capture spec

- Extraction: readability-style main-article extraction at click time (Mozilla
  Readability.js-class, embedded in the captured page's JS context — no custom
  heuristics; this is NEW BUILD, v1 had no extraction code); no background crawling,
  no headless fetches.
- Authenticated pages: whatever is in the DOM at capture moment is captured (user
  initiated); never re-fetched later.
- Dedup/versioning: keyed by normalized URL + content hash; recapture creates a new
  version, retrieval uses latest.
- Failure modes: SPAs/infinite-scroll capture visible viewport text only; PDFs and
  paywalled-partial captures are out of scope for the test (deferred). When extraction
  returns nothing usable, the UI shows "Couldn't extract this page" and offers raw
  visible-text capture as an explicit fallback; failed extractions never enter the corpus.
- Extraction-confidence logging: every capture logs a confidence score (opt-in,
  class-only telemetry) so quietly-mediocre extractions surface as clusters before
  they poison retrieval — the failure mode that passes every loud check.

### Ask/citation spec

- Retrieval: FTS5/BM25 over **spans** — paragraph-level chunks split on blank lines /
  structural breaks, clamped to 20–120 words, stored with `(captureID, charStart,
  charEnd)` offsets. Splitter rules (deterministic, one owner file, unit-tested on
  fixture documents): >120-word paragraphs split at sentence boundaries (hard cut
  only when no boundary exists); <20-word chunks merge with their nearest neighbor;
  offsets index into the stored normalized extraction string — never live DOM — so
  they survive recapture; span IDs are `{captureID}:v{n}:{spanIdx}`. Citations
  reference span IDs; the golden-set gate scores against these same spans.
- Grounding rule: answers may cite ONLY retrieved capture spans. Generation runs a
  validate-and-retry loop: draft answer → each cited span is checked by a second
  constrained-model pass ("does this span support this claim?" → yes/no) → unsupported
  citations cause regeneration of that claim; one retry max, then the claim is dropped;
  if no span clears relevance, the assistant refuses ("that's not in what you've
  captured"). Refusal is a feature, not a bug. "Clears relevance" is operational, not
  vibes: refuse when fewer than the top-k retrieved spans beat a minimum BM25 score τ,
  calibrated on the founder's dev captures (k<1 refuses immediately). τ drifts as the
  corpus grows — recalibrate at every eval gate or the ≥95% refusal number below is
  unfalsifiable. Refusals come in two honest flavors: "nothing you've captured covers
  this" (offer capture) vs "captured, but no span here supports it." Dropped claims
  stay visible — the answer contract records which claims were retried out so the UI
  renders honest gaps. An empty corpus gets a warm first-run state with a primary
  action ("Capture a page and I can answer from it"), never blank. Constrained
  decoding shapes output format only — support verification is this explicit loop.
- Golden-set eval gate (part of product quality gate): a 50-question set built from the
  founder's own captures, run on the M1 8GB floor machine; PASS requires ≥90% of answers
  whose cited spans actually support them and ≥95% correct refusals on out-of-corpus questions. No external users see the build until this passes. Charter written
  before W3: exact bucket counts — out-of-corpus bucket n≥20, since at the 95% bar a
  10-question bucket tolerates zero misses; expected answers authored up front in a
  fixed format; a ≥20-question hand-labeled calibration subset scores verifier
  precision/recall (the support-checker is the same class of small model — unmeasured,
  its errors contaminate the gate); decode params pinned (temperature 0 or fixed seed)
  so gate runs reproduce. Harness exists by end of W3 so the W4 run is calibration,
  not construction.

### Security posture (read-cite hardening)

Captured text enters model context and can carry injected instructions. Mitigations:
captures are delimited and labeled as untrusted data, never as instructions; the answer
contract permits output only as grounded summary + span references (no tool calls, no
URL fetching, no action execution — there is nothing to hijack into doing); adversarial
injection fixtures (hidden-text payloads per Brave/Trail-of-Bits patterns) run in the
test suite as regression tests. Residual, decided not deferred: authenticated-page
captures sit plaintext in SQLite — tolerable for enthusiasts, material for the
professional cohort this revision recruits. W1 decides between disclosing FileVault
reliance explicitly in the docs and encrypting the capture DB with a keychain key
(one-day item).

### Bridge protocol (the surface that killed v1)

One typed JSON message inventory between web chrome and native, defined before any UI
code and specified as a protocol, not a name list (one-page BRIDGE-SPEC.md lands in
W1 before chrome work): `tabs.create/select/close/list`, `nav.go/back/forward/reload`,
`omnibox.submit`, `bookmark.add/list/remove` (bookmarks persist in the local SQLite
store, not chrome localStorage), `capture.request/captured/capture.failed`,
`ask.request/stream-chunk/done/refused/cancel`, `settings.get/set`,
`session.restore`. Dot-delimited throughout — the v1-era hyphenated outlier is
normalized now, while it's free.

- Envelope: every message carries `{id, method, payload, err?}`; `stream-chunk` frames
  echo the request `id` so chunks correlate to their ask even across a chrome reload;
  terminal states are explicit — `done`, `refused`, or a typed error, never a
  dangling stream.
- Errors: one shared error shape across every handler — `nav.go` failures,
  `omnibox.submit` failures, store errors included; unknown methods get a typed
  error, not silence.
- `ask.cancel`: streaming local generation must be cancellable — without it users eat
  the full generation and agents improvise.
- Auth: v1 required a per-session token injected into served HTML because arbitrary
  web pages can reach the scheme handler. Carry it forward: tokenless/mismatched
  calls are rejected at the bridge (pattern preserved in `archive/v1`'s
  `WebChromeHandler.swift` header).
- `session.restore` gets real semantics: payload shape, tabs persisted in SQLite,
  replay ordered after chrome load — it's one of the nine gated flows.

Every chrome call must map to a registered handler — enforced by the contract test
resurrected from v1's `WebChromeBridgeContractTests` pattern (regexes adapted to the
v2 file layout and new message names), wired into CI as a merge gate.

## Measurement

All metrics below require instrumentation specified now:
- **Attribution:** each of the 50 contacted testers receives a personal tokenized
  download link; install events carry only the token (no content, no identity beyond
  token→tester mapping the founder keeps by hand). Day-7 retention = token seen on
  two distinct days ≥5 apart.
- Opt-in anonymous counters (session starts, ask-session counts, capture counts,
  domain-class of captured pages — news/arxiv/docs/internal-tool; class only, never
  URLs; crash-free sessions; ask-latency p50/p95, client-computed) POST to a
  Cloudflare Worker free-tier endpoint (~$0 marginal at this scale); no URLs, no page
  content, ever. Decliners are covered by attribution tokens + check-ins.
- Weekly 60-second self-report check-in (five quick questions, emailed reply):
  satisfaction, "was this for work?", "does answers-stay-on-this-Mac matter for what
  you do?", and ask-quality probes on tester-shaped content — tester genres differ
  from the founder's golden-set corpus, so ask-quality is probed, not assumed. Floor:
  if <60% of active testers respond by week 2 of the test, automated gate scoring is
  void and judgment falls to a manual review of tokens + whatever self-reports exist —
  decided explicitly, not silently.
- Pricing probe triangulated three ways (five email replies is too thin a reed for the
  GREEN memo): the week-4 anchor email stays; a clearly-marked, inert "Pro, coming
  later" entry point shows in-app from week 3; 15-minute interviews with the ≥3
  weekly-active testers collect price anchors directly. Replies counted by hand.
- Weights hosting: GitHub Release assets on this repo's public releases ($0).
- Denominators: "contacted waitlist" = exactly the 50 testers emailed in The
  Assignment; install % uses that 50 as denominator; day-7 retention uses installers. Out-of-cohort recruits (e.g., Arc-refugee communities) are excluded from all gate math — they extend the conversation, not the criteria.

## Success Criteria

Demand gate — judged once at week 6 after first external install:
- GREEN requires ALL of: ≥20% of contacted waitlist installs; ≥30% of installers return
  at day 7; ≥3 users run an ask-session weekly without prompting; ≥5 substantive replies
  to the pricing probe.
- RED if ANY of: <15% install, <25% day-7 retention, zero pricing-probe replies → trash
  or pivot; archive stays archived.
- Between green and red: one two-week iteration targeting whichever criterion failed —
  install miss → distribution/recruiting fix; retention miss → product fix; pricing
  silence → probe redesign — then re-judge against the same numbers.

Statistical honesty: n=50 with a 20% install target carries a 95% confidence interval
of roughly ±11 points. These gates are directional kill-tripwires — the correct use —
not measurements for extrapolation, fundraising decks, or self-congratulation.
Interpret them privately, the same discipline as the dead landing-page counter.

Objective-function linkage (the $8M question): GREEN does not mean the consumer browser is a business — no outcome of this test validates reachability of $8M, and the memo says so in writing rather than letting GREEN be misread as "on track." Week-6 GREEN triggers that written decision memo, due within 7 days of week-6 scoring (momentum dies in ambiguity), weighing consumer paid tier vs professional/team tier (where category money signal lives — scored from the Measurement section's work-signal data) vs YC application with traction evidence. RED triggers trash/pivot per
criteria above. The project continues only while evidence accumulates toward the stated
objective function, never around it.

Product quality gate (pre-condition for showing ANYONE):
- Nine core flows flawless: launch/restore, new tab, navigate, back/forward, search,
  bookmark, capture page, ask-with-citation, tab-orientation switch (or documented
  vertical-only fallback if timeboxed out). Everything else hidden.
- Verified by scripted CDP E2E tests covering exactly those flows on every push, plus
  the bridge contract test and the screenshot-diff suite — not unit-test counts. The
  Zen-bar checklist is part of this gate: <7/8 at the W2/W4 scorings blocks external
  exposure regardless of E2E green.
